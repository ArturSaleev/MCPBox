# Участие в разработке MCPBox

[English](CONTRIBUTING.md) · [Документация](docs/website/ru/README.md) · [Сообщения об уязвимостях](SECURITY-ru.md)

Принимаются сообщения об ошибках, небольшие улучшения, документация и переводы. Issues и PR можно писать на русском или английском. Перед большой доработкой опишите проблему в feature request, чтобы согласовать объём.

## Куда обращаться

- **Ошибка:** [Bug report](https://github.com/ArturSaleev/MCPBox/issues/new?template=bug_report.yml) с минимальными шагами воспроизведения.
- **Новая возможность:** [Feature request](https://github.com/ArturSaleev/MCPBox/issues/new?template=feature_request.yml) с описанием проблемы и желаемого результата.
- **Уязвимость:** только по [SECURITY-ru.md](SECURITY-ru.md). Не раскрывайте детали в публичных Issues и PR.
- **Настройка:** сначала проверьте [диагностику](docs/website/ru/troubleshooting.md). Discussions не требуется для участия; если документированный сценарий не работает, используйте Bug report.

## Локальная разработка

Нужны Go 1.26+ и Node.js/npm, совместимые с Vite из `html/package.json`. Из корня своего fork или checkout:

```bash
npm --prefix html ci
npm --prefix html run build
GOWORK=off go build -o MCPBox .
GOWORK=off go test ./...
```

После UI-изменений пересобирайте frontend, затем Go-бинарник: в него встроен `internal/httpapi/ui/dist`. Соблюдайте принятую в репозитории схему учёта generated assets. Vite dev server не имеет настроенного API proxy и не заменяет запуск полного приложения.

Запускайте собранный бинарник в отдельном доступном для записи каталоге с тестовыми данными. По умолчанию рядом с ним хранятся `mcpbox.db`, `package_store/`, `knowledge_base/`, `.mcpboxpro/`. `go run` использует временный бинарник. Не направляйте тесты на рабочую базу и не используйте production-секреты.

В текущих исходниках оба listener по умолчанию локальные: админка `38181`, MCP `38182`. Прямой сетевой доступ и отличия опубликованного v1.3.0 описаны в [сетевой конфигурации](docs/website/ru/network-access.md).

## Границы изменений

- Решайте одну задачу; несвязанное форматирование и рефакторинг выносите отдельно.
- Для Go используйте `gofmt`, для frontend — стиль соседнего кода. В `html/package.json` есть build/dev, но нет отдельных lint/test-команд.
- Добавляйте содержательные регрессионные тесты изменённого поведения, особенно для авторизации, изоляции проектов, лимитов выполнения и состояния. Для правок документации backend-тесты не нужны.
- Сохраняйте пользовательские базы, настройки и данные интеграций. По возможности применяйте аддитивные миграции, описывайте влияние на обновление и откат.
- Не добавляйте секреты в код, fixtures, снимки, журналы и generated assets. Примеры должны использовать синтетические данные.
- RagBox — отдельная интеграция. Сохраняйте её данные и границы; не добавляйте посторонние интеграции.
- Обновляйте обе языковые версии документации при изменении поведения. Сохраняйте совместимые имена `/api/pro/*` и `MCPBOX_PRO_*`, если не предусмотрен план миграции.

## Проверки

Выполните проверки по объёму изменений и укажите фактические результаты. Для backend обычно нужен `GOWORK=off go test ./...`; для конкурентного кода может потребоваться целевой `go test -race`. Для UI пересоберите frontend и проверьте готовое приложение. OAuth, AI-клиенты, RagBox требуют отдельных интеграционных проверок: unit-тесты не подтверждают внешнее подключение.

Проверка ссылок:

```bash
python3 scripts/check-doc-links.py
python3 scripts/check-doc-links.py --external --published-ref main
```

Публичная проверка рассчитана на уже опубликованные в `main` файлы: новые страницы могут давать ошибку до merge. Локальная проверка намеренно выявляет ссылки на неотслеживаемые Git файлы. Для сетевых проверок нужен `curl`; примеры localhost пропускаются.

Для проверки упаковки задайте `RELEASE_DIR` на отдельный тестовый каталог. Поддерживаемый скрипт — `./build-release.sh`; `all` собирает шесть плоских бинарников и `SHA256SUMS`. Не перезаписывайте рабочую установку и её базу ради теста упаковки.

## Pull requests

Опишите проблему, итоговое поведение, проверки и влияние на миграцию/безопасность. Честно укажите, что не проверено. Добавьте ссылку на Issue, если он есть. Используйте PR template; для UI полезны снимки без секретов. Небольшое исправление не требует отдельного feature proposal или обещания сроков.

Уважайте других участников: обсуждайте код, избегайте личных нападок и не публикуйте чужую частную информацию. Вклад предоставляется под [Apache-2.0](LICENSE); сохраняйте необходимые уведомления сторонних компонентов.

## Подпись вклада (DCO)

Каждый коммит в pull request должен быть подписан. Подпись создаётся флагом `git commit -s` (длинная форма `--signoff`): к сообщению коммита добавляется строка-трейлер:

```text
Signed-off-by: Имя Фамилия <name@example.com>
```

Имя и email должны идентифицировать автора вклада. Трейлер может стоять в любом месте блока трейлеров, но он обязателен в каждом коммите pull request.

Подпись подтверждает, что вы вправе предоставить вклад под [Apache-2.0](LICENSE), в смысле [Developer Certificate of Origin 1.1](https://developercertificate.org/). Это подтверждение, а не передача авторских прав: права на ваш вклад остаются у вас.

Pull request с неподписанными коммитами или с подписью, чьи имя и email не совпадают с автором коммита, не принимаются. Чтобы добавить пропущенную подпись, измените коммиты через amend или rebase и запушьте заново.
